# JARVIS — архитектура

## Стек

| Слой | Технология | Почему |
|---|---|---|
| Оболочка | Tauri v2 (2.12), WebView2 | нативное окно, малый размер, без Electron/Node-рантайма |
| Нативный слой | Rust + `windows` 0.62 (Win32, COM, WinRT) | прямой доступ к Core Audio, GSMTC, UIA, WMI |
| Асинхронность | Tokio | сеть, процессы, таймауты, отмена |
| UI | React 19 + TypeScript + Motion 14 | пружинная анимация формы острова |
| Хранение | SQLite (`rusqlite`, bundled) | история, задачи, настройки |
| Секреты | Windows Credential Manager (`CredWriteW`) | ключи API не попадают на диск в открытом виде |

Python и Electron не используются. Node.js нужен только для сборки фронтенда.

## Агент

Характер: системный промпт описывает Джарвиса как собеседника (тёплый,
остроумный, со своим мнением, честный, помнит пользователя через
`memory_save`), блок «предпочтения пользователя» берётся из настроек
«Характер» (имя, «ты»/«вы», манера). В голосовом режиме — разговорная речь,
интонация через пунктуацию, всё произносимое пишется словами.


Один ход: контекст (время, активное окно, недавние окна, папки, память) →
модель с инструментами → для каждого вызова: разбор аргументов, оценка риска
по аргументам и политике (вложения, приватность, имена элементов UIA) →
подтверждение при необходимости → выполнение с таймаутом и отменой →
результат `{ok, summary, data}` обратно модели. Ошибки возвращаются модели
для восстановления (до `max_steps`). Независимые безопасные вызовы идут
параллельно. Ход завершает только модель — ответом без вызовов
инструментов: досрочный выход после первого успешного шага обрывал
запросы вида «открой X и сделай Y». Лимит провайдера (429 +
`Retry-After`) выдерживается: ожидание, выученный лимит в минуту,
равномерная подача запросов, обратный отсчёт в UI.

Риск: **low** — сразу; **moderate** — подтверждение (по умолчанию, один раз
на инструмент в разговоре; при включённом режиме полного управления
`agent.fullControl` / `Автопилот ⚡` выполняется без запроса); **high** —
подтверждение всегда, даже на автопилоте. Решения и выполнения moderate/high
пишутся в `audit_log`.

### Исполнительные инструменты и Notch Hub

* **Живой план (`mission_plan`, `AgentEvent::PlanUpdated`)**: для многошаговых
  задач (от 3 шагов) агент публикует и обновляет чек-лист шагов
  (`pending / running / done / failed`), отображаемый над потоком сообщений в
  чате (`MissionPlanCard`) и в полосе активной миссии на острове (`AgentMissionBar`).
* **Notch Hub (`hub.rs`, `ipc_hub.rs`)**: потокобезопасное состояние поверх
  SQLite (`hub_tasks`, `focus_sessions`, `shelf_items`, `routines`) с событиями
  `hub:tasks`, `hub:focus`, `hub:shelf`, `hub:routines`:
  * **Задачи и повестка**: дата `YYYY-MM-DD`, время `HH:MM`, цветовая метка.
  * **Фокус**: секундный тикер работает только во время активной неснятой с паузы
    сессии; по достижении нуля записывает сессию в `focus_sessions`, закрывает
    привязанную задачу и озвучивает завершение через `hub::request_tts`.
  * **Полка (`Tray`)**: файлы (с живой проверкой `Path::exists()`), ссылки и
    заметки.
  * **52-недельный стрик активности (`hub_activity_get`)**: агрегирует реальные
    данные за 364 дня из SQLite (`focus_sessions`, закрытые `hub_tasks`,
    `audit_log`, реплики пользователя в `messages`) и дедуплицированные даты
    локальных Git-коммитов (`git log --since=365.days --format=%cs` с
    `CREATE_NO_WINDOW` по `project_roots`, недавним проектам VS Code и рабочей
    директории, с 5-минутным кэшем в ОЗУ). Никаких синтетических цифр.
  * **Сценарии (`routines`)**: при пустой таблице однократно засеваются 4
    русскоязычных плейбука (*Глубокая работа*, *Утренний брифинг*, *Порядок в
    окнах*, *Диагностика ПК*); запуск открывает рабочее пространство и передаёт
    промпт агенту.
* **Исполнительный набор Win32 (`tools/executive.rs`)**: `selection_grab`
  (снимок буфера обмена → `Ctrl+C` → ожидание смены sequence number до 120 мс →
  восстановление исходного буфера), `window_layout` (`snapshot`, `restore`,
  `tile_pair` 50/50 или 65/35, `focus_clean` с проверкой координат через Win32),
  `system_diagnostics` (`GlobalMemoryStatusEx`, 150-мс замер `GetSystemTimes`,
  `GetDiskFreeSpaceExW`, `GetSystemPowerStatus`, топ-5 процессов по рабочему
  набору), `tasks_manage`, `focus_session`, `speak_aloud`.

## MCP

Серверы хранятся в `kv` (`mcp.servers`), их последние списки инструментов — там же
(`mcp.tools`), поэтому агент знает инструменты, не запуская серверы. Инструмент
называется `mcp__<сервер>__<инструмент>` (до 64 символов). `Registry` отдаёт их
вместе со встроенными и выполняет через `Hub::call`. Первый вызов запускает
сервер: `initialize` → `notifications/initialized`, затем `tools/call`. Сервер,
к которому не обращались 10 минут, останавливается. stdio-сервер работает в
Job Object без консольного окна. Команда ищется в PATH так же, как в cmd
(`npx` → `npx.cmd`), `%VAR%` в аргументах раскрываются. HTTP-клиент ведёт
`Mcp-Session-Id` и `MCP-Protocol-Version`, принимает ответ JSON или SSE и
переподключается, если сервер забыл сессию. Сервер может прислать
`tools/list_changed`, тогда список перечитывается. На `ping` и `roots/list` клиент
отвечает, остальные запросы сервера отклоняет. Риск: `readOnlyHint` → low,
`destructiveHint` → high (подтверждается всегда), иначе moderate. OAuth и старый
транспорт SSE не поддерживаются.

## Голос

Два движка с общим UI острова (события `voice:state`, `voice:level`,
`voice:transcript`):

**Локальный (по умолчанию), sherpa-onnx на CPU.** cpal: микрофон → моно →
фильтр + ресемплинг → PCM16 16 кГц чанками по 100 мс → Silero VAD (нейросетевой;
пауза внутри фразы до 0,9 с не режет её, шум и музыка — не речь) → GigaAM v3
(RNN-T от Сбера для русской речи, с пунктуацией; 0,2–0,6 с на фразу) →
`Agent::voice_turn`: обычный ход агента (тот же промпт с припиской «ответ будет
озвучен», инструменты, подтверждения, история чата) → текст ответа стримится в
`PhraseSplitter` (первая клауза сбрасывается уже от 24 символов на `,`, `—`, `:`,
`;`, последующие — по границам предложений) → потоковый синтез `Speaker` →
очередь вывода 24 кГц.

**Потоковый синтез речи (TTS) и универсальная озвучка (`voice/edge.rs`, `voice/tts.rs`, `ipc_tts.rs`).**
По умолчанию без ключей и скачивания используется `Speaker::Edge` — протокол
Microsoft Edge ReadAloud Neural HD (`wss://speech.platform.bing.com/...`) с
вычислением токена `Sec-MS-GEC` v2 (округление системного времени с автопоправкой
сдвига часов по заголовку `Date` при 403), IPv4-приоритетным кэшем адреса
(`TCP_NODELAY`) и пулом прогретых TLS WebSocket-соединений (`WARM_POOL`), благодаря
чему первая порция звука 24 кГц моно `i16` PCM (покадровое декодирование MP3 в
чистом Rust через `nanomp3`, полностью совместимое с `+crt-static`) приходит за
~235–300 мс. Курируемые голоса в начале каталога: `edge:ru-RU-DmitryNeural`,
`edge:ru-RU-SvetlanaNeural`, `edge:en-US-AndrewMultilingualNeural`,
`edge:en-GB-RyanNeural`. Повторяющиеся фразы до 140 символов отдаются из
двухуровневого кэша `PcmCache` (64 записи в ОЗУ за ~40 мкс + персистентный
дисковый LRU в `%LOCALAPPDATA%\dev.jarvis.desktop\tts_cache` за ~5–6 мс). Если
сеть недоступна до выдачи первого чанка, `Speaker::Edge` прозрачно переключается
на скачанный локальный `NeuralVoice` (Supertonic 3 / Piper) → системный
`WindowsSpeaker`. Вызов `VoiceManager::speak` (`tts_speak`, `tts_stop`,
`tts_status`, `tts_benchmark`, инструмент `speak_aloud`, автоозвучка чата)
открывает только выходной поток `AudioOutput` без обращения к микрофону и шлёт
события `tts:state` и `voice:level` (30 Гц), оживляя глаза острова во время речи.

Начало речи пользователя поверх ответа очищает очередь (перебивание); новая просьба во
время хода ждёт его окончания (последняя побеждает); «стоп»/«хватит» отменяют
всё; фраза, начатая меньше чем через ~2 с паузы, продолжает предыдущую и
объединяется с ней. Перед синтезом текст нормализуется (`ru_speech`), после
каждой фразы — пауза по её знаку препинания. Распознаватель держится в
памяти 3 минуты после сессии и выгружается.

Отклик на имя: сессия живёт в двух режимах — ожидание (`dormant`: остров
закрыт, уровни не шлются, фразы без имени отбрасываются молча) и разговор.
Переход по имени в начале фразы (`wake::addressed`), Ctrl+Alt+K или кнопке;
обратно — «стоп»/«хватит», «всё, спасибо»/«отбой», Esc, а с 23 ноября — сразу
после ответа: выполнив просьбу, Джарвис снова ждёт имени, если сам не задал
вопрос (тогда 12 с на ответ). Свёртывание после ответа, на чужую речь и на
ответ модели `∅` — без звука. Фраза с именем, построенная как рассказ, а не
просьба или вопрос («Джарвис у меня вчера завис, прикинь»), идёт модели как
`Heard::Unsure`: она может промолчать. Микрофон не переоткрывается между режимами. Если открыть его не удаётся,
слушатель повторяет попытки с нарастающей паузой, не показывая ошибку.

**Чьи это слова (`voice::intent::classify`).** Живые логи 20–21 ноября показали,
что при «любая фраза в разговоре — команда» Джарвис минутами отвечал песне, игре
и разговору дома («Вачем замуж», «Это моя», а «Алиса, нежно-белый цвет» запустила
shell-команды). Теперь фраза без имени проходит, только если:

* это точная команда устройства — плеер, громкость, яркость (`agent::fast`):
  «пауза», «дальше», «назад», «играй», «верни музыку», «громче»;
* или она построена как обращение к Джарвису: начинается с глагола-просьбы,
  это вопрос к «ты» из трёх слов и больше, «а завтра?» сразу после ответа или
  короткий ответ на его собственный вопрос. Такая фраза идёт модели как
  *ambient*-ход с пометкой «услышано без имени»: модель может ответить `∅`,
  и тогда ничего не говорится, в чате не остаётся следа, а Джарвис перестаёт
  слушать без имени;
* после «Слушаю», клика или Ctrl+Alt+K следующая фраза — команда, какой бы
  она ни была (10 с).

Команды плеера («пауза», «играй», «верни музыку», «дальше», «назад», голый
«стоп») работают без имени и при закрытом голосовом режиме — от любого голоса,
по выбору пользователя 21 ноября (`intent::media_run_command`): только точная
фраза плеера до трёх слов, не поверх собственного голоса Джарвиса в колонках, не
эхо его ответа и не во время задачи. Остальные фразы без имени, пока играет
музыка или фильм, не считаются вовсе.
Обращение к другому ассистенту («Алиса, …», «Окей, Гугл») игнорируется всегда.
Целое предложение чужой речи (три слова и больше) возвращает Джарвиса к ожиданию
имени. «Стоп»/«хватит» в конце фразы («…Джарвис, хватит. Стоп.») тоже стоп.
«Стоп» относится к Джарвису; к музыке — только если сам Джарвис ничего не
делает и фраза его и позвала («Джарвис, стоп» из тишины) либо прозвучала сразу
после «включи музыку». «Всё, спасибо», «отбой», «можешь отдыхать» закрывают
разговор: с именем — коротким ответом, без имени — молча.

Медиакоманды выполняются локально, без модели (≈150 мс вместо 3 с), и отвечают
по-человечески: «Играет «Про любовь» — Земфира», «Пауза». «Дальше» и «назад»
без уточнения считаются медиакомандой, только когда открыт плеер. На время
разговора играющие приложения приглушаются до 30 % (`platform::audio::duck`);
уровни возвращаются, если пользователь сам их не менял, а после сбоя
восстанавливаются при следующем запуске из `kv` (`voice.ducked`).

Модели не входят в установщик: «Настройки → Голос» скачивает их из релизов
sherpa-onnx на GitHub (`asr-models`, `tts-models`) с проверкой размера и
SHA-256 (из API релизов) и распаковывает `.tar.bz2` с защитой от выхода за
папку. sherpa-onnx открывает файлы по ANSI-пути — для профилей с кириллицей
используется короткий путь 8.3.

Почему не Whisper: первая версия на whisper.cpp (small) на живой речи давала
«Настой, пожалуйста, браузер» вместо «Открой…» и «Джарби» вместо «Джарвис»;
turbo без видеокарты распознавал фразу 18 с.

**Qwen Omni Realtime.** Те же чанки → `input_audio_buffer.append`. Ответ
`response.audio.delta` (PCM16 24 кГц) → очередь. `speech_started` очищает
очередь и отправляет `response.cancel`. Функции голосовой модели исполняются
тем же реестром и политикой риска; многошаговые задачи уходят в текстового
агента через `delegate_to_agent`.

Эхо-гейт (оба движка) глушит тихий сигнал микрофона, пока Джарвис говорит
через колонки; локальный VAD в это время засчитывает речь, только если она
на 12 дБ громче фона, а фразы, не прошедшие этот порог, отбрасывает.

## История буфера обмена

Всё локально, в той же SQLite (`clips`). Слушатель (`platform::clipwatch`) — скрытое
окно только для сообщений с `AddClipboardFormatListener`; серия обновлений одного
копирования схлопывается таймером 150 мс. `Clips::capture` (отдельный поток из пула
Tokio) читает снимок `platform::clipboard::snapshot` и отдаёт чистой функции
`clips::prepare`, которая решает, что сохранить:

* копия, помеченная программой как приватная (форматы Windows
  `ExcludeClipboardContentFromMonitorProcessing` и `CanIncludeInClipboardHistory`
  со значением 0 — так делают менеджеры паролей), **не читается вообще**;
* программы из списка в настройках (подстрока имени процесса);
* текст, похожий на секрет (закрытый ключ, токен известного формата, JWT, номер
  карты по Luhn, длинная случайная строка) — выключается в настройках;
* порядок выбора: файлы → текст → картинка. Картинка берётся из формата `PNG` или
  `CF_DIBV5`/`CF_DIB`, хранится чистым PNG, опознаётся по хешу пикселей, поэтому одна
  и та же картинка из двух программ — одна запись. Миниатюра 200×100.

Одинаковое содержимое хранится один раз (повторное копирование поднимает запись
наверх и сохраняет закрепление). Закреплённые не истекают и не считаются в лимитах;
остальные — до `maxItems` записей и `keepDays` дней, картинки — в бюджете 96 МБ.
Поиск — подстрока без учёта регистра (в том числе кириллицы) по тексту, именам
файлов и программе. При выключенной записи буфер не читается совсем.

Вставка (`Clips::paste`): запись кладётся в буфер и читается обратно (проверка), затем
`end_input(true)` возвращает фокус окну, откуда пришли, ждём его до 0,5 с и жмём
Ctrl+V. Остров не активируется при клике, поэтому при вставке мышью фокус и не
уходит; при вставке с клавиатуры (хоткей, поиск) окно временно фокусируемо, как у чата.
Что именно появится в окне, решает программа, — Джарвис подтверждает только то, что
запись в буфере и Ctrl+V отправлен.

Агент: инструмент `clipboard_history` (list / get / copy / paste). Чтение записей —
подтверждение, как у `clipboard_read`, если не включено «Читать буфер обмена без
вопроса»; вставка подтверждается всегда.

## Окно-остров

* Одно прозрачное окно-холст 760×640 логических px, верх-центр рабочей
  области основного монитора; `WS_EX_TOOLWINDOW` (нет в панели задач),
  `WS_EX_TOPMOST`, `WS_EX_NOACTIVATE` (через `focusable=false` в tao),
  без скругления и рамки DWM.
* **Прозрачные области не блокируют клики**: окно по умолчанию
  `WS_EX_TRANSPARENT` (`set_ignore_cursor_events(true)`). Поток
  `island-tracker` читает `GetCursorPos` и включает интерактивность, только
  когда курсор над текущей формой острова. Форму присылает фронтенд при
  смене состояния (целевой прямоугольник, не каждый кадр).
  Интервал опроса адаптивный: 16 мс рядом с островом, 40 мс в 120–400 px,
  100 мс дальше, 250 мс когда остров скрыт. Низкоуровневый хук мыши
  отвергнут: он стоит в пути каждого движения мыши во всей системе.
* **Перетаскивание файлов**: нажатая кнопка мыши вне острова + курсор в зоне
  приближения → окно временно становится интерактивным, и OLE drag-drop
  доходит до WebView2 (Tauri `onDragDropEvent`). Перетаскивание окон
  (`GUI_INMOVESIZE`) исключено.
* **Фокус**: клики по кнопкам острова не забирают фокус. Рабочее
  пространство вызывает `begin_input` (запоминает предыдущее активное окно,
  делает окно фокусируемым) и `end_input(restore)` (возвращает фокус,
  только если он всё ещё у острова).
* **Полноэкранные приложения**: хук `EVENT_SYSTEM_FOREGROUND` + таймер
  1,5 с + `SHQueryUserNotificationState` → остров скрывается.
* **Дисплеи**: скрытое top-level окно ловит `WM_DISPLAYCHANGE` и
  `WM_SETTINGCHANGE(SPI_SETWORKAREA)`; смена DPI — через
  `ScaleFactorChanged`. Перерасчёт позиции с дебаунсом 400 мс.

## Наушники и Bluetooth (`bluetooth.rs`, `platform/bluetooth.rs`)

Windows: сопряжённые устройства читаются из дерева PnP (CfgMgr32) и группируются
по контейнеру устройства. Узел `DEV_` даёт имя, класс устройства, VID/PID и
подключение (`{83DA6326-…} 15`), заряд — свойство `{104EA319-…} 2`, которое
показывает и «Параметры» (HFP или GATT Battery). Для подключённых наушников Apple
пассивный LE-скан читает их собственную рекламу «proximity pairing»: каждый
наушник, кейс, зарядка, «в ухе», крышка. Берётся только реклама той же модели
(PID) и рядом (RSSI ≥ −72 дБм), скан идёт, только пока такие наушники подключены.
macOS: всё то же из `system_profiler SPBluetoothDataType -json`.

Сервис держит сутки замеров на устройство (`kv: bluetooth.history`), считает
расход по последнему падающему отрезку (не меньше 5 % за 15 минут) и сколько
ещё хватит, предупреждает на 20 % и 10 % (`bluetooth:low`) и шлёт
`bluetooth:devices` при изменениях. Опрос — раз в 5 с, пока наушники подключены,
иначе раз в 20 с (macOS — 30/90 с).

## Обновления (`updater.rs`)

`tauri-plugin-updater` читает подписанный `latest.json` из последнего релиза
GitHub через 45 с после запуска и раз в шесть часов (`updates.autoCheck`).
Ничего не ставится само: карточка на острове, «Настройки → Основное» и пункт
трея ставят обновление по клику — пакет скачивается, подпись minisign
проверяется публичным ключом из `tauri.conf.json`, NSIS ставит его в режиме
passive, приложение перезапускается. `latest.json` собирает release-воркфлоу из
`.sig`-файлов сборок Windows и macOS. Закрытый ключ — секреты репозитория
`TAURI_SIGNING_PRIVATE_KEY(_PASSWORD)`.

## Установщик Windows (`installer/`)

Отдельный маленький крейт на tao + wry: одно окно в стиле продуктового
установщика (приветствие → шаги с прогрессом → «Готово»). Внутри — NSIS-пакет,
который собирает Tauri (встраивается на этапе сборки через `JARVIS_PAYLOAD`); он
запускается тихо (`/S`), поэтому деинсталлятор, ярлыки и автообновления работают
как раньше.

## Принципы

* Каждое действие проверяется чтением результата (громкость читается
  обратно, запуск приложения ждёт его окно, WM_CLOSE проверяет, закрылось ли
  окно).
* Блокирующие вызовы Windows — только в `platform::blocking` (пул Tokio +
  COM MTA на потоке).
* Ошибки сериализуются как `{ code, message }` с русским текстом без
  технических трассировок; детали — в журнале
  `%LOCALAPPDATA%\dev.jarvis.desktop\logs\jarvis.log`.
